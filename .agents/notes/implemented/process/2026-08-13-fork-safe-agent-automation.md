# Agent Note: Fork-safe agent automation

Status: implemented

English | [中文](2026-08-13-fork-safe-agent-automation.zh.md)

## Problem

`Ornn8/deepseek-harness` forks the upstream repository to run its GitHub-agent automation pipeline, but four failure modes prevent that fork from operating autonomously.

1. The Issue policy check reads `config.json`, whose `organization` and `repository` are both `deepseek-harness`, so `policy.mjs pr` queries `/repos/deepseek-harness/deepseek-harness/...`. A fork PR therefore receives a 404 from the `requested_reviewers` endpoint and the job fails.
2. The Issue lifecycle check hardcodes `owner: deepseek-harness` and `repositories: deepseek-harness` on its `create-github-app-token` step, and that step requires `vars.DSH_ISSUE_APP_CLIENT_ID` plus `secrets.DSH_ISSUE_APP_PRIVATE_KEY`. The fork configures neither, so the action fails with "client-id must be set to a non-empty string".
3. One caller workflow combines Issue dispatch, Codex review, DSH repair, and merge intent. It treats mutable labels and a head-only status as durable state, grants unrelated jobs a coupled permission surface, and relies on `repository_dispatch` even while the receiving workflow exists only in the pull request rather than on the default branch. A blocking review can therefore fail to wake DSH during bootstrap, and a later base update can leave a successful head status that no longer represents the reviewed base/head pair.
4. Required CI jobs default to upstream-only larger-runner labels. A personal fork has no runners with those labels, so required checks remain queued without executing.

## Decision

Each check derives its coordinates from the repository it actually runs in instead of naming the upstream repository, and the App-gated lifecycle becomes inert when its credentials are absent.

Failed or cancelled top-level Agent Issues, Agent PR Rework, Agent PR CI Repair, and Agent PR Review runs enter a separate event-driven recovery workflow. The recovery controller verifies the exact reusable controller SHA in the source run's `referenced_workflows`, locates the matching durable Issue or pull-request status record, rechecks the live Issue state or exact PR pair, and records no more than three retries. Comments and labels remain audit projections; a forged record cannot authorize a retry. The third exhausted attempt remains an `agent/dsh-failed` or `automation/review-failed` dead-letter and does not invoke a model.

`policy.mjs` splits `process.env.GITHUB_REPOSITORY` (`owner/repo`) into `organization` and `repository` and prefers them over the `config.json` defaults; local and test runs leave the variable unset and keep the checked-in defaults. Every REST/GraphQL path that previously interpolated `config.organization`/`config.repository` now interpolates those derived constants.

ProjectV2 and organization Issue Fields are organization-only GitHub features: the REST `issue-field-values` endpoint 404s on personal-account repositories and the GraphQL `organization(...)` root does not exist for them. `config.json` therefore declares these capabilities explicitly (`project.enabled` and `issueFields.enabled`), and a personal-account repository disables both instead of failing every pull request on unsupported metadata. Disabled capabilities skip their endpoints entirely and `validateIssue` drops the Type, Priority, and Status checks; resolving-Issue references and repository-local labels stay enforced. An enabled capability still fails loud on any API error, and `policy.mjs` selects the GraphQL owner root from the live repository metadata (`user(...)` for a personal account, `organization(...)` for an organization), so an organization-capable fork keeps the full policy without changing code.

`issue-lifecycle.yml` adds `vars.DSH_ISSUE_APP_CLIENT_ID != ''` to the job-level `if`, so a credential-less repository (including this fork) skips the job instead of failing it, and derives the App installation from `github.repository_owner` and `github.event.repository.name` so an App-installed fork addresses its own installation rather than upstream.

The target repository uses separate workflows for Issue dispatch, exact-pair PR review, trusted rework feedback, explicit landing, and health. Each caller pins the reusable workflow revision in `uses`; the controller revision, role worker, and runner selection are controller-owned rather than caller inputs. Required CI jobs retain the upstream repository's larger runners and select standard GitHub-hosted runners in a fork unless its repository variable explicitly selects a self-hosted failover pool. CI repair and CI-triggered landing declare the configured CI workflow name as a literal `workflow_run.workflows` subscription so GitHub can register the listeners, then compare the delivered name with `DSH_AUTOMATION_CI_WORKFLOW` before dispatch. Every privileged pull request listener, including project lifecycle and Issue policy, uses `pull_request_target` and checks out the default-branch policy, so a pull request cannot replace a privileged workflow definition before it reaches the default branch. Review-submitted events are not privileged inputs; the automated BLOCK label is only a visible projection of the exact review CheckRun and immutable repair WorkRequest.

The automation repository exposes one Agent Worker invocation and terminal-receipt interface. Runtime-specific Adapters start and observe DSH Web, ChatGPT Desktop, or a JSON-speaking command; target workflows map the `review` and `change` roles to a configured worker id. The roles use separate `agent-reviewer` and `agent-change` runner registrations, processes, work directories, concurrency groups, and health jobs.

The review worker receives an exact base/head checkout with no Actions credential and performs read-only inspection. A job-scoped Actions token publishes the pending or final `codex/review` CheckRun, the English review comment, and projection labels. The CheckRun stores the originating Actions run URL as opaque external metadata because GitHub may normalize its visible details URL; landing fetches that run and verifies the pinned reusable controller reference. A BLOCK verdict records the exact pair and terminates the review task after the controller publishes an immutable, idempotent repair WorkRequest for the `change` role. The receiving workflow starts independently, validates the WorkRequest fields, live head, review evidence, and label, and then invokes its configured change worker. A completed failed workflow whose name equals `DSH_AUTOMATION_CI_WORKFLOW` creates a separate request keyed by run id and attempt; the controller requires that name, failure conclusion, matching PR number, and exact current head before the change worker may inspect its logs or modify the branch.

A PASS verdict emits `dsh-land` instead of enabling long-lived auto-merge. The landing controller accepts only a current non-draft PR to the repository default branch, requires an exact base/head PASS record and the configured exact-head `all checks passed` CheckRun from the GitHub Actions App, repeats those checks immediately before a squash merge, and otherwise exits without changing the PR. Installation and online diagnostics independently enforce the branch-protection requirements because a workflow token cannot read repository administration settings. A successful configured CI workflow run retries landing after pending checks complete.

After a push to the repository default branch, reconciliation compares each same-repository PR's recorded base commit with the current default-branch commit and updates a stale base regardless of GitHub's transient mergeability state. That mutation uses the verified host GitHub credential on the change-role runner, so GitHub emits ordinary pull-request events that rerun both CI and review; using the Actions job token would suppress them. Current pairs that did not need a branch update receive an explicit review dispatch only when they lack trusted exact-pair evidence. Backlog and bounded recovery also use explicit `repository_dispatch` events. A trusted Issue may contain one strict `agent-work:v1` JSON routing declaration: `ready` queues its `change` role, `hold` remains inert, and open `dependsOn` Issues defer it until an Issue-close event reevaluates the backlog. The declaration's canonical field hash supplies stable request identity, while the worker rereads the live declaration and dependencies before invoking a model. Backlog may also reclaim a legacy `agent/dsh` Issue that has no closing PR or terminal failure; workflow concurrency and stable request identity prevent a second model turn. A marker-verified CI baseline Issue without a declared branch enters this same queue on the deterministic `agent/issue-<number>` branch. The protected default-branch listeners and pinned reusable controller revalidate the live Issue or exact PR pair before invoking a model. The manual health workflow checks each configured worker on its own runner plus the pinned controller and GitHub access without invoking a model.

## Alternatives considered

**Gate the lifecycle on the private key with a step guard.** A step-level guard can test `secrets`, but a skipped job is the explicit "inert" state the requirement names; `vars.DSH_ISSUE_APP_CLIENT_ID` is set together with the private key in the repositories that own the App, so the job-level variable test is the correct and sufficient fork-safety condition.

**Keep one caller workflow for all agent events.** A single file is shorter, but most event deliveries produce skipped jobs, every change couples unrelated trigger and permission review, and bootstrap behavior is difficult to distinguish from steady-state behavior. Separate callers keep event ownership and permissions visible while reusable workflows retain the implementation.

**Use a head-only status with GitHub auto-merge.** A status attached only to the head can survive a base change, while auto-merge retains merge intent after the evidence that created it is stale. An exact-pair review record plus a short-lived landing transaction binds approval to both revisions and rechecks immediately before mutation.

**Poll GitHub for Issues, comments, or check completion.** Polling adds idle model or controller activity and still introduces a detection interval. Native GitHub events drive every model invocation; reconciliation and health remain deterministic and model-free.

## Consequences

The policy and lifecycle checks now pass on this personal-account fork, whose `config.json` declares both organization-only capabilities disabled; resolving-Issue references and repository-local labels remain the enforced policy surface there. The capability flags change no upstream behavior: `GITHUB_REPOSITORY` equals the configured coordinates there, `project.enabled` and `issueFields.enabled` stay `true`, and the Project lookup still targets the owning organization through the `organization(...)` root.

A fork that later installs the issue-management App and wants lifecycle status updates must set `project.enabled: true` with the matching ProjectV2 number and title (plus `issueFields.enabled: true` and its `priorityField` when the repository uses organization Issue Fields) and provide both App credentials; the capability flags and workflow-level changes only make credential absence non-fatal and the App installation self-addressing, they do not provision a fork Project.

The target repository now contains more workflow entry files, but their logic remains in the dedicated automation repository and their immutable pin makes the deployed controller auditable. Labels remain operator-visible projections, not transport or approval evidence; comments contain the exact pair and visible DSH or Codex task identity needed to supervise a run. CI failure repair is event-driven and creates no model activity while checks are green.

Stopping one role runner leaves the other role operational; jobs for the stopped role remain queued in GitHub. Both registrations currently share one Windows host, network connection, DSH Web service where applicable, and persistent host GitHub login used by controller transport and change publication. Moving a role to another machine needs only its runner labels and machine-local worker configuration, while complete host and GitHub-App isolation remains separate security hardening.
